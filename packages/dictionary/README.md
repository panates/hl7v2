## About

HL7 v2.x dictionary for Node.js. This package provides version-specific definitions for segments, data types, and messages, for every version from 2.1 to 2.9 (2.1, 2.2, 2.3, 2.3.1, 2.4, 2.5, 2.5.1, 2.6, 2.7, 2.7.1, 2.8, 2.8.1, 2.8.2, 2.9). It is used by the `hl7v2` parser and serializer to understand message structures.

### How the dictionaries are built

- **Every version is defined as HL7's own v2 XML schemas define it.** A field the version withdrew is absent - the fields after it keep their numbers - and a choice of segments (ORM_O01's OBR, RQD, RQ1, RXO, ODS, ODT) is held as one, of its alternatives.
- **A trigger event is its message structure.** ADT_A04 and ADT_A08 are the very definition of ADT_A01, the structure the standard assigns them.
- **A version is built the first time it is used**; the others cost nothing until then.
- **A definition identical in several versions is one object**, shared by all of them and frozen. Change a dictionary through `extend()`, `overwriteSegments()` or `overwriteTypes()`, which copy what they change - a definition cannot be modified in place.

The data (`data/hl7-data.js`) is generated by `support/build-dictionary.mts` from:

- **the HL7 v2 XML schemas** - "HL7 Version 2.x Messaging Schemas" and "Version 2 v2.xml XML Schemas for HL7 Version 2.5 and earlier" from [HL7's V2 product suite](https://www.hl7.org/implement/standards/product_brief.cfm?product_id=185). They are licensed by HL7 and not in the repository: download them (an HL7 account is needed) into `support/hl7-schemas/`;
- **HAPI HL7v2's event map**, for which structure a trigger event uses - the schemas do not say;
- **the [`hl7-dictionary`](https://www.npmjs.com/package/hl7-dictionary) package**, for what the schemas leave out: descriptions of segments, data types, messages and groups, field lengths before 2.6, the C and B optionalities, and a few definitions the early schemas name without defining.

```bash
$ node support/build-dictionary.mts      # regenerate data/hl7-data.js
$ node support/compare-dictionary.mts    # report where the dictionaries differ from the schemas
```

With the schemas in place, the tests compare every version with them, field by field; without them those checks are skipped.


## Usage Example

### Accessing a Dictionary

```typescript
import { dictionaries, HL7Version } from 'hl7v2-dictionary';

const dict25 = dictionaries[HL7Version.v2_5];

console.log('Version:', dict25.version);
console.log('PID Segment definition:', dict25.segments['PID']);
```

### Extending a Dictionary

```typescript
import { dictionaries, HL7Version } from 'hl7v2-dictionary';

const customDict = dictionaries[HL7Version.v2_5].extend({
  version: '2.5-custom' as any,
  segments: {
    Z01: {
      desc: 'Custom Segment',
      fields: {
        1: { type: 'ST', desc: 'Custom Field 1', opt: 'R' }
      }
    }
  }
});

console.log('Custom Segment:', customDict.segments['Z01']);
```

## API

### HL7Dictionary

The `HL7Dictionary` class holds definitions for a specific HL7 version.

#### Properties

- `version: HL7Version` - The HL7 version this dictionary represents.
- `segments: Record<string, HL7SegmentDefinition>` - Segment definitions.
- `types: Record<string, HL7DataTypeDefinition>` - Data type definitions.
- `messages: Record<string, HL7MessageDefinition>` - Message structure definitions.

#### Methods

##### .extend()
Creates a new dictionary by extending the current one with new or overridden definitions.
Given segments and types are merged over the current ones, and given messages added to them; only those are copied - every other definition is shared with the current dictionary.
`extend(args: { version?: HL7Version; segments?: Record<string, DeeperPartial<HL7SegmentDefinition>>; types?: Record<string, DeeperPartial<HL7DataTypeDefinition>>; messages?: Record<string, HL7MessageDefinition>; }): HL7Dictionary`

example
```typescript
const extendedDict = dict.extend({
  segments: {
    PID: {
      fields: {
        1: { desc: 'Overridden Description' }
      }
    }
  }
});
```

##### .overwriteSegments()
Merges new segment definitions into the current dictionary.
`overwriteSegments(segmentsDefs: Record<string, DeeperPartial<HL7SegmentDefinition>>): void`

example
```typescript
dict.overwriteSegments({
  PID: {
    fields: {
      1: { desc: 'New Description' }
    }
  }
});
```

##### .overwriteTypes()
Merges new data type definitions into the current dictionary.
`overwriteTypes(typeDefs: Record<string, DeeperPartial<HL7DataTypeDefinition>>): void`

example
```typescript
dict.overwriteTypes({
  ST: {
    desc: 'String Data Type'
  }
});
```

### Utility Functions

##### .findNearestHL7Version()
Finds the nearest available HL7 version in the dictionary for a given version string.
`findNearestHL7Version(version: HL7Version): HL7Version`

example
```typescript
import { findNearestHL7Version, HL7Version } from 'hl7v2-dictionary';

const nearest = findNearestHL7Version('2.5.2' as any);
// Returns HL7Version.v2_5_1 - the newest version not newer than 2.5.2
```

##### Dates and times

HL7 writes DT as `YYYY[MM[DD]]`, DTM/TS as `YYYY[MM[DD[HH[MM[SS[.SSSS]]]]]][+/-ZZZZ]` and TM as `HH[MM[SS[.SSSS]]][+/-ZZZZ]`. A value read from a message is kept as written - its precision and offset are part of it - once checked. A `Date` is written in local time with its offset, as HAPI HL7v2 writes it; without an offset the standard reads a time as the sender's local time.

- `toHL7DateTime(value: Date | string): string`, `toHL7Date(...)`, `toHL7Time(...)` - the codecs of DTM/TS, DT and TM: check an HL7 value and return it unchanged, format a `Date` (or an ISO 8601 string).
- `formatHL7DateTime(date: Date, options?: { offset?: boolean }): string` - `20250102060405.678+0300`; `offset: false` leaves the offset out.
- `formatHL7Date(date: Date): string` - `20250102`, the local date.
- `formatHL7Time(date: Date, options?: { offset?: boolean }): string` - `060405.678+0300`.
- `parseHL7DateTime(value: string): Date` - read in its offset, or as local time without one; missing parts are their lowest (`2025` is 2025-01-01 00:00).

```typescript
import { formatHL7DateTime, parseHL7DateTime } from 'hl7v2-dictionary';

formatHL7DateTime(new Date()); // "20250102060405.678+0300"
parseHL7DateTime('20250102030405-0500').toISOString(); // "2025-01-02T08:04:05.000Z"
```

In `hl7v2`, `getDate()` reads a value as a `Date`: `field.getDate()`, `component.getDate()`, `message.getDate('PID-7')`.

### Interfaces

#### HL7SegmentDefinition
- `desc?: string` - Description of the segment.
- `fields: Record<string, HL7FieldDefinition>` - Map of field index to field definition.

#### HL7FieldDefinition
- `type: string` - The data type of the field.
- `desc?: string` - Description of the field.
- `opt?: HL7DatatypeOptional` - Optionality ('R', 'O', 'S', 'C', 'B').
- `rep?: HL7DatatypeRepetition` - Repetition (number or 'infinite').
- `len?: number` - Maximum length.
- `table?: number` - Associated table number.
- `item?: number` - HL7 data element number (PID-5 is item 108).
- `minLen?: number` - Minimum length.
- `confLen?: number` - Conformance length (2.7+): the length a receiver must keep at least. From 2.7 on most string fields have this instead of `len`.
- `truncate?: boolean` - Whether a longer value may be truncated (2.7+): `true` is HL7's `#`, `false` its `=`.

#### HL7DataTypeDefinition
- `desc?: string` - Description of the data type.
- `fields?: Record<string, HL7FieldDefinition>` - Components of the data type (if complex).

#### HL7MessageDefinition
- `desc?: string` - Description of the message.
- `segments?: Record<string, HL7MessageSegmentsDefinition>` - Message structure definition: groups and segments keyed by name, ordered by `idx`.

#### HL7MessageSegmentsDefinition
- `idx: number`, `min?: number`, `max?: number`, `desc?: string`
- `segment?: string` - The segment type, when the key is not it: a segment repeated among its siblings is keyed as HAPI HL7v2 keys it (the second `PID` of ADT_A17 is `PID2`).
- `choice?: boolean` - A choice: the message carries one of its `segments` (an alternative is a segment or a group). `HL7Message.buildStructureTree()` matches the one present.
- `aliases?: string[]` - For a group, the names the same group has in other versions of the message. Each version keeps its standard names; `HL7MessageNode.getNode()` finds a group by either.
- `segments?: Record<string, HL7MessageSegmentsDefinition>` - A group's own structure.
